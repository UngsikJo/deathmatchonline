Deathmatch Online ERD

Supabase PostgreSQL에 둘 테이블의 관계도입니다. Supabase가 관리하는 auth.users에 직접 만드는 테이블 6개가 붙습니다. 이동·체력·쿨다운 같은 실시간 전투 상태는 게임 서버 메모리에만 있고, DB에는 계정, 경기 시작·결과, 연승, 필요한 이벤트만 기록합니다(10.2).

  • 정확히 1
  • 0 또는 1
  • 0개 이상
  • 1개 이상
  • FK 없는 참조
  • PK기본키 FK외래키 UQ유일 ?NULL 허용
  • PRD 11.1에 없던 컬럼
  • 서버만 기록브라우저에서 쓰기 불가 (12장)

PRD에 없어서 정한 것

  • matches.created_at 추가. 경기 행은 전투 전에 저장되므로(11.2-1), 준비 단계에서 취소되거나 복구 작업이 정리할 경기(11.2-8)에도 기준 시각이 필요합니다. started_at은 카운트다운이 끝나 전투가 시작된 시각으로 보고, 전투 전에 취소되면 NULL입니다.
  • match_participants.character_key 추가. 경기 중 캐릭터 교체 거절과 재접속 시 같은 캐릭터 복귀(14.1), 반복되는 우세 조합 관찰(18장)에 필요합니다. 캐릭터 정의는 코드에 있으므로 테이블 대신 키 값만 둡니다.
  • match_events의 컬럼 전부. PRD에는 용도(기권·접속 단절·운영 조사)와 보관 기간 제한만 있습니다.
  • 이름만 붙인 것: 두 참가자 ID는 player1_id·player2_id, 최종 체력은 final_hp, outcome 값은 win·loss·draw.

구현 전에 정할 것

  1. 탈퇴 시 기록 처리. 삭제·익명화 방식이 미정이라(9.1) auth.users를 가리키는 FK의 ON DELETE를 아직 정할 수 없습니다. Supabase 문서 예시의 on delete cascade는 profiles에는 맞지만, matches에 걸면 한 사람이 탈퇴할 때 상대방의 경기 기록까지 지워집니다. 경기 쪽은 SET NULL(익명화, 컬럼을 NULL 허용으로)과 RESTRICT 중에서 골라야 합니다.
  2. queue_or_match_id 분리. 대기열은 DB 테이블이 없어 이 컬럼에 FK를 걸 수 없습니다. 경기를 가리킬 때 쓰는 match_id(NULL 허용, FK)와 대기열 티켓 값을 나누면 경기 참조는 FK로 보호됩니다.
  3. 참가자 이중 저장. matches.player1_id·player2_id와 match_participants 2행이 같은 사실을 따로 저장합니다. 정산 함수 한 곳에서 함께 쓰거나 한쪽을 빼야 둘이 어긋나지 않습니다.
  4. 연승 단위. 지금은 계정 단위입니다(16.1 제안, 캐릭터를 바꿔도 연승 유지). 캐릭터별 연승으로 바뀌면 player_stats의 키가 (user_id, character_key)가 됩니다.
  5. reason = draw의 겹침. 동시 KO와 시간 종료 동점은 ko·timeout과도 겹칩니다. 무승부는 winner_id IS NULL과 outcome으로 판단하고 reason에는 종료 원인만 남기는 방법이 있습니다.

DB에 두지 않는 것

  • 대기열과 진행 중 전투 상태(좌표·체력·쿨다운·궁극기 게이지·다운). 게임 서버 메모리에만 있고 DB에는 매 프레임 기록하지 않습니다(10.2). 결과를 저장하기 전에 서버가 멈추면 그 경기는 무효입니다(11.2).
  • 캐릭터 4종과 스킬 수치. packages/shared 코드에 두고, 경기마다 rules_version으로 어떤 규칙으로 치렀는지 남깁니다(10.3, 11.1).
  • 음량·승리 후 자동 매칭 설정. PRD에 저장 위치가 없습니다. 다른 기기에서도 유지해야 하면 테이블을 추가해야 합니다.
