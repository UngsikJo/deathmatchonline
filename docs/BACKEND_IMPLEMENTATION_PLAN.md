## 3. 다음 구현 순서

### 먼저: 개발 Supabase와 프로필

1. 운영과 분리한 개발 Supabase에서 001→002를 검토·적용합니다. 기존 경기 데이터가 있으면 이관 계획부터 수립합니다.
2. 실제 두 계정으로 가입·인증·트리거·RLS를 확인합니다. 기존 Auth 계정의 프로필·통계 backfill은 별도 작업입니다.
3. 서버가 `getUser(token)`으로 인증한 계정 UUID를 사용하고 닉네임은 DB 프로필에서 읽도록 F02를 연결합니다. 브라우저의 닉네임·승패·게이지를 DB의 확정 값으로 신뢰하지 않습니다.
4. 서버 전용 DB 자격 증명을 준비하되 웹 `VITE_` 변수·Git·로그에 넣지 않습니다. 준비 단계에서는 비밀 키 환경 변수를 새로 연결하지 않았습니다.

### 다음: 잠금과 경기 생성·시작

대기표를 발급한 뒤 계정 PK 잠금을 원자적으로 획득합니다. 만료된 잠금 회수는 DB 시각과 조건부 갱신을 사용합니다. renew/release는 기존 `user_id`, 참조 ID, 상태, lease 시각이 모두 일치할 때만 성공해야 하며 오래된 방의 해제가 새 대기를 지우면 안 됩니다.

두 명을 배정할 때 새 DB 경기 UUID를 생성합니다. `matches` 1행·`match_participants` 2행·캐릭터·규칙 버전·참가 잠금 전이를 **한 트랜잭션**으로 저장합니다. 게임은 이 성공을 확인한 뒤 준비·카운트다운으로 넘어갑니다. 참가자 수 지연 제약 때문에 REST insert를 세 번 따로 호출하는 구현은 사용할 수 없습니다.

카운트다운이 끝날 때 서버 인스턴스 소유권과 preparing 상태를 확인한 후 DB 시각으로 active 전이합니다. `started_at`과 새 경기 상태 초기화는 같은 수명 사건이어야 합니다. 게스트는 이 정식 저장 경로에 보내지 않습니다.

### 핵심: 원자적 정산 RPC와 재시도

후속 migration의 서버 전용 RPC를 구현합니다. 아래 함수명은 제안이며 **현재 생성된 RPC가 아닙니다.**

| 제안 경로                                                             | 트랜잭션 책임                                             |
| --------------------------------------------------------------------- | --------------------------------------------------------- |
| `claim_participation`, `renew_participation`, `release_participation` | 중복 참가·만료·기존 소유권 조건                           |
| `create_match`                                                        | 경기·참가자 2행·잠금 이동·선택 고정                       |
| `start_match`                                                         | 서버 소유권·상태 확인, 시작 시각 기록                     |
| `settle_match`                                                        | 동일 경기 재시도·충돌 검사, 결과·양쪽 통계·연승·잠금 해제 |
| `cancel_match`, `void_expired_match`                                  | 시작 전 취소·장애 무효, 통계 보존·잠금 정리               |

정산 순서는 경기 행 잠금 → UUID 순으로 두 통계 행 잠금 → 기존 결과 비교 → 경기/개인 결과/통계 갱신 → 소유권이 같은 잠금 해제 → 커밋 → 영수증 반환입니다. 같은 경기·같은 승자·사유·참가자·최종 결과의 재요청은 기존 영수증을 반환하고 통계를 다시 더하지 않습니다. 다른 결과는 `settle_conflict`로 기록하고 기존 결과를 덮어쓰지 않습니다.

승리면 현재 연승+1·승+1, 새 최고 기록에만 최초 달성 시각을 갱신합니다. 패배·무승부면 현재 0·패/무+1이며 최고값은 유지합니다. 취소·무효면 통계를 바꾸지 않고 개인 outcome도 NULL입니다. 기존 전투 프로토콜의 void는 양쪽 연결 종료에도 쓰이므로 정산 명령을 만들 때 서버 장애와 연결 종료의 원인을 명시해야 합니다.

현재 `DuelRoom.finalize()`는 동기 메모리 정산 전에 `finalized = true`를 설정합니다. 이를 DB 저장소로 그대로 대체하면 실패 후 재시도가 막힙니다. 후속 구현은 `pending / saving / committed / retrying` 같은 내부 상태를 두고 성공 전까지 확정 결과·다음 매칭을 열지 않아야 합니다. `onLeave()`의 잠금 해제도 finalizing 소유권을 지키도록 조정해야 합니다.

### 마지막: 조회·장애 복구·게임 연결

- 자기 최근 경기·자기 영수증·공개 순위 조회를 구현하고 클라이언트에는 허용된 필드만 전달합니다. 이메일은 제외합니다.
- 저장 성공 뒤 클라이언트가 끊겨도 동일 영수증을 재조회합니다. DB 장애를 감추기 위해 자동으로 메모리 저장에 성공 처리하지 않습니다.
- 저장 전 서버가 사라진 진행 경기는 lease 만료 후 void 처리합니다. 이미 completed인 경기의 확정 결과는 취소하거나 재계산하지 않습니다.
- 이벤트 보관 주기·기권/준비 이탈 제한·다중 서버 경쟁 검증을 붙입니다. 탈퇴 익명화는 별도 정책과 migration으로 처리합니다.
- F04의 캐릭터 선택·기술을 실제 서버와 연결한 뒤 경기별 `character_key`·`rules_version`을 검증합니다. 이번 계약에서 사용한 4개 키가 현재 게임에 선택 기능을 추가한 것은 아닙니다.

## 4. 검증과 완료 조건

```sh
npm run check
npm run test:db
```

`test:db`는 PostgreSQL 실행 파일 `initdb`, `pg_ctl`, `psql`이 있는 환경에서 실행합니다. 실행 중인 로컬 DB에 접속하거나 클라우드 DB를 초기화하지 않습니다. 새 임시 데이터 폴더·Unix 소켓만 사용하고 TCP 리스너는 열지 않습니다. CI에는 PostgreSQL 설치 단계를 별도로 준비해야 하며 현재 CI 예시를 자동 활성화하지 않습니다.

다음 항목이 통과하기 전에는 영구 저장 완료로 표시하지 않습니다.

- [ ] 실제 Supabase Auth·JWT·REST/RPC에서 두 사용자 권한 확인.
- [ ] 정산 같은 요청 10회·서로 다른 결과·양쪽 동시 요청에서 한 번만 반영.
- [ ] 서로 다른 경기에서 같은 계정 동시 정산·잠금 만료 회수·오래된 heartbeat/release 경쟁.
- [ ] 커밋 전 실패·응답 유실·프로세스 재시작·재접속 후 영수증 복원.
- [ ] 최고 기록 최초 달성 시각 보존, 캐릭터를 바꿔도 계정 연승 보존.
- [ ] 원자적 RPC·비동기 서버·저장 중 UI를 연결한 실제 두 클라이언트 검증.
- [ ] 탈퇴 익명화·이벤트 보관 정책 확정과 검증 후 production 제한 재검토.

## 5. 사용자 준비가 필요한 항목

개발 Supabase 프로젝트, 이메일 인증·테스트 계정, 이후 메일 발송에 필요한 SMTP 설정을 준비해야 합니다. 비밀 키는 채팅이나 Git에 올리지 않고 서버 환경에만 설정합니다. 운영 전에 탈퇴 시 경기 기록을 어떻게 익명화할지와 이벤트 보관 기간을 확정해야 합니다. 현재 구조는 DB 연결 정보 없이도 로컬 계약 검증을 실행할 수 있습니다.
