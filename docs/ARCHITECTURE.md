# 개발 기반 구조

## 데이터 흐름

브라우저가 `duel` 방에 참가하면 서버가 닉네임과 개발 ID 또는 Supabase 토큰을 검증합니다. 계정의 동시 참가를 잠근 뒤 게임 렌더러의 `ready` 메시지를 기다립니다. 두 명이 준비되면 3초 카운트다운을 거쳐 전투를 시작합니다.

브라우저는 입력 순번·이동 축·스킬만 전송합니다. 서버는 형식과 속도를 검증하고 `Simulation`을 30틱/초로 실행합니다. 전체 공개 스냅샷을 20회/초 메시지로 전송합니다. 아직 Colyseus Schema 델타 압축을 사용하지 않습니다. 적은 플레이어 수에서 규칙을 검증하기 위한 출발점이며, 실제 메시지 크기는 이후 측정해 최적화합니다.

게임 상태에는 서버의 시뮬레이션 시간이 들어 있습니다. 클라이언트는 마지막 수신 시각 이후 최대 150ms까지만 시간을 추정하여 쿨다운·예고 표시가 멈춘 연결에서 무한히 앞서지 않게 합니다.

## 책임 경계

- `shared/rules.ts`: 수치, 스킬 정의, 충돌·이동 계산. 클라이언트가 사용하더라도 서버 판정 권한이 넘어가지는 않습니다.
- `shared/protocol.ts`: 메시지 타입, 런타임 입력 검증, 연승 전이.
- `shared/simulation.ts`: 이동·시전·명중·체력·시간·승패. 네트워크와 분리하여 테스트합니다.
- `DuelRoom`: 방 수명, 준비, 입력 제한, 누적 재접속 예산, 정산 호출.
- `DevStore`: 프로세스 메모리의 테스트 전적. 서버 종료 시 사라집니다.
- `game/session.ts`: 연결, 재접속 토큰, 스냅샷·통계를 React와 Phaser에 공유합니다.
- `ArenaScene`: 입력 수집, 캐릭터·범위·투사체 렌더링. 체력이나 승패를 직접 결정하지 않습니다.

## 현재 의도적인 제한

첫 구현은 단일 프로세스입니다. 참가 잠금·정산 중복 방지도 메모리에 있으므로 여러 서버 인스턴스로 늘리면 안전하지 않습니다. 인증에 Supabase를 연결해도 전적이 영구 저장되지는 않습니다.

내 캐릭터는 입력에 따라 먼저 이동하며 서버 위치로 연속 보정합니다. 입력 이력을 마지막 처리 순번까지 재실행하는 방식은 아직 아닙니다. 상대는 보간합니다. 높은 지연에서 조작감이 충분한지는 검증이 필요합니다.

렌더링 모양과 실제 충돌 크기는 다릅니다. 플레이어 몸은 반지름 16, 맵은 공통 사각형 데이터입니다. 현재 Tiled 원본은 없으며 아트 반입 단계에서 공유 맵 데이터 생성기를 추가합니다. 돌진은 각 틱과 180ms 동작 구간이 겹치는 시간만큼 이동해 틱 경계에서도 거리를 보존합니다.

경기가 끝나면 결과를 한 번 정산하고 방을 잠급니다. 사용자는 방을 떠나 다음 상대를 찾습니다. 결과 방은 최대 60초 뒤 정리됩니다. 단절된 사용자가 결과 완료 후 복귀하지 못할 수도 있으며, 이를 해결하려면 영구 경기 기록 조회가 필요합니다.

## 영구 저장 도입 시 변경점

1. 방 참가 전 DB 경기·참가 레코드와 잠금을 생성합니다.
2. 경기 ID와 두 참가자의 결과를 서버 전용 PostgreSQL 함수 하나에서 정산합니다.
3. 해당 함수는 경기 상태 조건과 행 잠금으로 중복 정산을 막습니다. 클라이언트 호출은 허용하지 않습니다.
4. 정산 실패 시 결과 화면에 저장 중 상태를 표시하고 다음 매칭을 차단합니다.
5. 서버 장애로 남은 진행 경기·참가 잠금에 유효 기간을 두고 복구 작업을 작성합니다.
6. DB 결과 조회를 추가한 뒤 생산 환경 실행 제한을 재검토합니다.

SQL 함수·RLS는 실제 Supabase 테스트 프로젝트에서 두 사용자 권한과 중복 정산을 검증한 후 연결해야 합니다.
